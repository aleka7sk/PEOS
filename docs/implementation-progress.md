## PEOS-005 Binding Architecture Summary

The full binding architecture lives in **Packet G.B** (the consolidated Blueprint); this is
a pointer summary only, kept here so that Packets G.1–G.5 cannot silently reopen accepted
decisions. Do not treat this summary as a substitute for reading Packet G.B in full before
starting any G.1–G.5 work.

- **Dependency direction:** `peos/requirement → peos/relation → peos/core`. No cycle. `peos/requirement` does not import `peos/decision`.
- **§17–§23 architecture:** typed Requirement-specific wrappers around `relation.Relation` — not standalone records, not Requirement-aware validation inside `peos/relation`.
- Constructors accept typed semantic parts only and build the inner `relation.Relation` themselves; they **never** accept a pre-built `relation.Relation`.
- Requirement relationships have **no independent identity** (no ID field, no Ref type, no lifecycle, no revision history, no `id` JSON key) — per PEOS-005 §17.1.
- Requirement Supersession's lifecycle consequence has **exactly two** mandatory-explicit semantic states (consequence identified / explicitly no consequence); no conformant "unstated" state exists; a nil/optional pointer is an insufficient encoding.
- Requirement Supersession's governance action is a closed two-arm union (`core.DecisionOutcomeRef` | opaque Product-contract mechanism) — **not** `core.AuthorityRef`.
- **Waiver has no identity** — a value record owned by `peos/requirement`, not an Artifact Relation, no lifecycle. **Implemented by Packet G.5.I with no `core.Provenance` field** — an explicit correction applied to the Packet G.5 Blueprint's own proposal (Risk R-1) before implementation began.
- **Allocation is Product-owned** (`PROD`) — no SDK implementation debt, no implementation packet.
- **Dependency and Conflict participants use `RequirementParticipant`** (`participant.go`, introduced by G.3.I) — a closed two-arm union over `core.RequirementRef` and `core.RequirementArtifactRevisionRef`, mirroring `decision.InvalidationSource`. This is the only relationship-participant type in the package that is not fixed at Requirement Artifact Revision level; Derivation, Refinement, Decomposition, and Requirement Supersession all remain revision-only and do **not** use `RequirementParticipant` (Supersession confirmed this at implementation, per G.4/G.4.I).
- **`GovernanceAction`** (`governance.go`, introduced by G.4.I) is shared foundation, not Supersession-specific — a closed two-arm union over `core.DecisionOutcomeRef` and `core.VocabularyValue` (an established Decision Outcome, or a Product-contract-permitted mechanism). §27 Waiver defines its authorizing action in identical terms to §23, so **Packet G.5 is expected to reuse `GovernanceAction` directly, unmodified.**
- **Supersession's direction is inverted** relative to Derivation, Refinement, and Decomposition: source is the superseding (newer) participant, target is the superseded (older) one (§23.1). `Superseding()`/`Superseded()` name this; there is no `Source()`/`Target()` naming collision risk because the underlying `relation.Relation` accessors remain `Source()`/`Target()` regardless.
- **Supersession does NOT require Requirement-identity distinctness** — REQ-1/REV-2 superseding REQ-1/REV-1 is valid. Every PEOS-005 identity clause touching Supersession (§7, §23, §28.3, §35) is worded as preservation ("SHALL NOT merge," "SHALL retain"), never distinctness, unlike §18's and §20.1's direct distinctness language for Derivation and Decomposition.

## Deferred Architecture

### `[-]` Specialized Artifact Supersession enforcement (PEOS-002, recorded by Packet L.0.C)

- **Missing concept:** A typed Artifact Supersession wrapper that would enforce PEOS-002's specialized rules for that relation type — mandatory scope, rejection of direct self-supersession — and carry its two conditional items as typed fields.
- **Normative source:** `spec/002-artifact-model.md`, "Artifact Supersession" (`:717`–`:769`), whose six-item list is: exactly one superseding source subject; exactly one superseded target subject; the applicable scope; its provenance; the governance basis or authority "where required by applicable governance"; the resulting Lifecycle consequence, "if any". Also the Supersession Identity Invariant (`:948`–`:950`), the Supersession Acyclicity Invariant (`:952`–`:954`), and `:750` ("An Artifact or Artifact Revision SHALL NOT directly or transitively supersede itself").
- **What exists today — the workflow is representable, not blocked.** `core.RelationTypeArtifactSupersession` exists, and `relation.New(core.RelationTypeArtifactSupersession, source, target, provenance)` followed by `.WithScope(scope)` carries **all four unconditional items** of `:723`. Artifact Supersession is **not** listed in PEOS-002's minimum-conformance set (`:1053`–`:1064`). Nothing about this deferral makes a valid PEOS-002 state unrepresentable.
- **What is deferred:** (a) *enforcement* — nothing compels scope on a generic Relation, and nothing rejects `source == target`, so an invalid Supersession relation is structurally constructible; (b) *typed representation* of the two conditional items (`:729` governance authority, `:730` Lifecycle consequence), which today have no field and, per `peos/relation/relation.go`'s `WithExtension` documentation, must not be smuggled through `extension`.
- **What is NOT deferred and never was:** transitive acyclicity (`:748`, `:750`) remains repository-owned and unchanged — PEOS-002 `:622` states cycle validity is per-Relation-Type, and `peos/relation/doc.go` documents that assignment. This entry does not reopen it.
- **Existing decision this entry records rather than creates:** `peos/template/doc.go` already states, in its "Deliberately not modeled by this package" section, that "core.RelationTypeArtifactSupersession exists for it; a general PEOS-002 Artifact Supersession wrapper is peos/relation's or a future packet's concern, not this package's debt." Phase L.0 reported the deferral as unrecorded; Phase L.0.B found that package-level decision and downgraded the finding accordingly. Packet L.0.C records it here, where rule 10 says every deliberate non-implementation belongs.
- **Ownership or dependency that must be resolved:** Which package owns a specialized wrapper. `peos/relation` documents itself as structural-validation-only, so placing per-Relation-Type semantics there would contradict its own stated boundary; a new sibling package or an accepted amendment to `peos/relation`'s scope would be required first.
- **Future packet responsible:** Not yet named. Requires the owning-package decision above before any implementation packet can be scoped.

### `[-]` Template Migration (PEOS-009, Packet K.0 risk RK-1, applied by Packet K.1)

- **Missing concept:** A Template Migration construct carrying the nine items PEOS-009 requires every migration to identify — source Template Artifact Revision; target Template Artifact Revision; affected generated Artifacts or future applications; parameter mappings; transformation rules; information-loss risks; authority; provenance; applicable Validation requirements per PEOS-006.
- **Normative source:** `spec/009-template-contract.md`, "Template Migration" section (`:486`–`:504`), including "Every migration SHALL identify:" and "Migration does not rewrite historical Template Application Records or previously generated Artifact Revisions."
- **Reason for deferral:** **PEOS-009 never states what a Migration is.** It is not declared an Artifact, not declared an immutable record, and not declared an Artifact Relation; it does not appear among the items a Template Artifact Revision SHALL identify (`:173`); and `peos/core` carries no `RelationTypeTemplateMigration` alongside the three relation types it *does* define for PEOS-009 (`GeneratedFrom`, `TemplateComposition`, `TemplateSpecialization`) — evidence the reference layer's authors did not model it as a relation either. Three candidate ontologies are each representable and the specification chooses none: a Revision-owned value on `TemplateContent`; a standalone non-identity-bearing value; or a repository-and-Decision-owned workflow governed by `:630` ("Template generation or migration that requires governance approval SHALL use Decision semantics, as defined by PEOS-004"). Inventing one would assert structure PEOS-009 does not define, which CLAUDE.md prohibits. The single concession made is `CompatibilityDeclaration.MigrationRequirements()`, an opaque descriptor satisfying the compatibility declaration's own "migration requirements, where applicable" scoping item (`:471`) without modeling Migration itself.
- **Ownership or dependency that must be resolved:** Whether PEOS-009 is amended to assign Migration an ontology, or whether an explicit architectural decision records one (and if so, which of the three candidates) before any packet implements it.
- **Future packet responsible:** Not yet named; would require a PEOS-009 amendment or an accepted architecture decision first, not merely an SDK packet.

### `[-]` Delegation (PEOS-004)

- **Missing concept:** An authority-grant record — identity; delegator (`core.ActorRef` | `core.AuthorityRef`); delegate `core.ActorRef`; delegated scope; effective period or condition; applicable constraints; revocation conditions.
- **Normative source:** PEOS-004 :824-839 ("A delegation MUST identify: the delegating Actor or authority; the receiving Actor; the delegated scope; applicable constraints; the effective period or condition; revocation conditions when applicable.")

### Recorded, no action required — Ref() API Decision (Phase L.2, deferred additive API)

Phase L.1 (finding L1-03) noted that `validation.Plan`/`PlanRevision`, `quality.Profile`/`ProfileRevision`, `runtime.Contract`/`ContractRevision`, `template.Template`/`TemplateRevision`, and `decision.RecordRevision` all expose a `Ref()` convenience method, while `requirement.Requirement`, `requirement.Revision`, and `decision.Record` do not — the reference-construction path for those three exists (`core.NewRequirementRef(id)`, `core.NewDecisionRef(id)`), just not as a same-package method.

Phase L.2's packet instruction required a bounded review against five explicit criteria before adding any `Ref()` method, defaulting to **no addition** on reasonable doubt. Evaluated: (1) the method would return an already-existing core reference type — true; (2) no new semantics — true; (3) the convention is already dominant in peer packages — true, four of nine aggregate/revision pairs already have it; (4) **the addition would materially improve the full cross-package workflow example — not established.** `docs/consumer-guide.md` section 7 and `examples/crosspackage/workflow_example_test.go` both construct `core.RequirementRef` explicitly via `core.NewRequirementRef(requirementArtifact.ID())`, and that explicit construction is itself pedagogically useful — it is the exact moment the guide's section 4 ("why cross-package composition goes through core") is demonstrated, and hiding it behind a same-package convenience method would remove that visibility rather than add it. (5) Given (4) does not clear the bar, this entry is decided by the packet's own explicit default: reasonable doubt exists, so the convenience API is deferred rather than added.

**Decision: do not add `Ref()` to `requirement.Requirement`, `requirement.Revision`, or `decision.Record` in this release.** The existing `core.New*Ref(id)` path is documented prominently in `docs/consumer-guide.md` sections 4 and 7 instead. This is a candidate for a v1.1 minor-version, purely additive API change (README's Release Contract clause 5 already permits it) — not a v1.0.0 blocker, and not a deferred *specification* concept (unlike every other `[-]` entry in this section), so it carries no normative source and no future-packet placeholder.

### Recorded, no action required — Packet H.3 Consolidated Audit finding H3-04 and NOTEs H3-05..H3-07

These are **not** deferred architecture; they are recorded here only so they are not lost between conversations, per the same convention as G-06/G-07 above:

- **H3-04 — `core.ExecutionOutcome`'s constructor and API shape diverge from its seven `peos/core/vocabulary.go` siblings.** `NewExecutionOutcome` returns `(ExecutionOutcome, error)` and validates a non-zero `VocabularyValue`; `NewArtifactType`, `NewArtifactRole`, `NewRelationType`, `NewValidationMethod`, `NewClaimType`, `NewClaimOutcome`, and `NewCorrectionKind` all return a plain value with no validation. `ExecutionOutcome` is also the only one of the eight with an `Equal` method (matching `lifecycle.TransitionOutcome`'s own precedent, which also has one). **Decision: preserve current behavior.** This is not a PEOS-006 violation — PEOS-006 states nothing about constructor signatures — and harmonizing the family upward (or downward) would be a breaking change to seven existing, already-shipped constructors with no PEOS-006 driver for making it now. Zero-value `Marshal` for `ExecutionOutcome` also intentionally matches sibling behavior (emits the inner zero `VocabularyValue`'s form, which does not round-trip) rather than adding a rejection unique to this one type; `ExecutionRecord` already rejects a zero outcome before it can reach the wire, so the practical exposure is nil. Revisit only if a future packet touches the whole vocabulary family for an unrelated reason.
- **H3-05 — Some PEOS-006 "SHALL identify" bullets are unqualified yet implemented as optional.** Independently re-verified: `ExecutionRecord`'s `criteria`/`events`/`producedEvidence`/`reliedUponEvidence` and `limitations`/`uncertainty` have direct normative support for optionality (the Validation Model Overview's "zero or more" cardinality language, and §"where material" for limitations/uncertainty); `PlannedActivity`'s `criteria`/`expectedEvidence`/`prerequisites` rest on the same "zero or more" basis plus the specification's own zero-criteria evaluation clause. Only `ExecutionRecord.environment` rests on inference alone, and mandating it would make legitimate minimal records unrepresentable. No action required.
- **H3-06 — Conjunctive `IsZero` on `ExecutionRecord` and `Claim` permits an unreachable partially-populated value in principle.** Identical in shape to `relation.Relation`, `requirement.Waiver`, and every H.1 type; unreachable through any exported constructor or modifier. No action required.
- **H3-07 — Three PEOS-006 non-conforming patterns (Certification as Validation Method, Acceptance as Validation Method, Validation Outcome Used as Governance Authority) are Product-owned, not structurally prevented.** Independently re-verified as genuine layer limits rather than avoidable gaps: PEOS-006 keeps the Validation Method vocabulary explicitly open ("This list is illustrative and is not a closed vocabulary"), so a Product declaring `acme:certification` cannot be prevented without violating that openness. This package predeclares no Method constants at all as the one structural mitigation available. No action required without a PEOS-006 spec clarification.

## PEOS-007 Closure Summary (recorded by Packet I.4)

PEOS-007 (Quality Model) is **closed (`[x]`)**. This section is the permanent closure record;
the full packet-by-packet history remains in the Packet Progress table above and is not
repeated here.

### Delivered ontology

- **Quality Profile** as an Artifact (`Profile`, wrapping `core.Artifact`, `ArtifactTypeQualityProfile`), using ordinary `core.ArtifactRevision` (`ProfileRevision`) — no Quality Profile Version of any kind.
- **Quality Profile Revision-owned content** (`ProfileContent`): `Characteristic` (two scopings — Profile-defined term, or exact external vocabulary), `Measure`, `Threshold`, `Target`, `Constraint`, `NormalizationRule`, `AggregationRule` — none independently identified, revisioned, or lifecycle-bearing.
- **Profile applicability** (`ProfileApplicability`) as a closed unrestricted/scoped discriminator, mandatory and unreachable by modifier.
- **Measurement Record** (`MeasurementRecord`), composing `validation.ExecutionRecord` by named field and adding exactly the observed value, unit, and scale PEOS-006 has no field for.
- **Validated Quality Claim** (`Claim`), composing `validation.Claim` by named field, fixing the Claim Type to `core.ClaimTypeQuality`, and enforcing the one PEOS-007-specific rule (`:297`'s Requirement-as-own-criterion prohibition) through a single shared validation path reached from every constructor, modifier, and JSON path.
- **Three additive `core.CriterionRef` arms** (`quality_threshold`, `quality_target`, `quality_constraint`), reusing the existing `QualityElementCriterionRef` payload — the only `peos/core` change PEOS-007 required.

### Preserved architecture

- Artifact and Revision identity inherited unchanged from PEOS-002; no parallel Quality Profile identity space.
- No owned value (`Characteristic`, `Measure`, `Threshold`, `Target`, `Constraint`, `NormalizationRule`, `AggregationRule`) carries independent identity, revision, or lifecycle — verified structurally by AST and reflection absence tests, not merely by convention.
- Every citable owned value is referenced exactly as (`ProfileRevision.Ref()`, profile-local `LocalKey`) via `core.QualityElementCriterionRef` — the exact composite reference, never a flattened or opaque encoding.
- **Per-kind local-key namespaces**: uniqueness enforced within each of the seven owned-value collections; the same key may legitimately name a value in two different collections, because every reference already determines its own target collection.
- Immutable value semantics throughout: every modifier returns a copy; every collection is defensively copied on input and output; a failed modifier returns the zero value with the receiver untouched.
- Strict constructor completeness: no mandatory field is reachable only through a later modifier; `NewProfileContent`'s six-argument signature (including `normalizationRules`, required because a `Measure` may reference one before any modifier could attach it) is the sole exception explaining an argument beyond the originally-anticipated set, and it exists for exactly this reason.
- No hidden repository resolution: the value layer proves what a Claim or record *cites*; whether a cited Profile Revision or key actually exists elsewhere is repository-owned.
- No execution semantics for Normalization or Aggregation Rules: both are mandatory-description value structures: this package computes no normalized value and no aggregate.
- **No PEOS-006 regression at any point in the sequence**: `peos/validation` was never modified by any PEOS-007 packet (confirmed by `git diff` between every pair of pre/post commits across I.1, I.2, I.3.A, I.3.B); `TestNonSatisfactionClaimMayUseSameRequirementAsSubjectAndCriterion` and `TestPEOS006StillAcceptsWhatPEOS007Rejects` both still pass, proving PEOS-006 remains correctly more permissive than the PEOS-007 wrapper on the one point where the two intentionally diverge.

### Final cardinality policy

- **Profile-owned collections have no universal minimum cardinality.** PEOS-007 states no minimum anywhere in the specification (verified: zero occurrences of "one or more" / "at least one" / "non-empty" alongside any of the seven collections), and the repository's own drafting convention — nine of ten PEOS specifications state a minimum explicitly wherever they intend one, and `validation.PlannedActivity` already ships the identical "unqualified SHALL-identify permits empty" reading for three of its own list items — settles the question the same way PEOS-007 itself does not.
- **Empty `ProfileContent` is representable**: valid scope, explicit applicability, non-zero provenance, all seven owned-value collections empty.
- **Constraint-only** is representable: a Quality Constraint depends on no Characteristic or Measure and is independently citable as a `quality_constraint` criterion — the decisive case that overturned the original ≥1-Characteristic/≥1-Measure minimums.
- **Characteristic-only** is representable: a Characteristic is a complete definitional or external-reference act on its own, independently citable as a `quality_characteristic` criterion with no Measure in existence.
- **Rules-only** is representable: neither Normalization nor Aggregation Rules require a referrer to be valid.
- **Measure, Threshold, and Target references remain conditionally, mandatorily resolved** — a Measure's Characteristic key must resolve; a Measure's optional Normalization Rule key must resolve if present; a Threshold's and a Target's Measure key must resolve. This is what makes Measure-only, Threshold-only, and Target-only Profile Revisions **still rejected** — not by any cardinality rule, but because the reference each of them carries cannot resolve against an empty target collection. Removing the two unjustified minimums therefore admits no incoherent or dangling-reference state.
- **Completeness and publication readiness belong to repository/Product policy**, not to this package's value layer — the same boundary already drawn for unit semantics, scale semantics, threshold comparison, and aggregation execution.
